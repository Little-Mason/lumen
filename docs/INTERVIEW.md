# 面试讲法与亮点清单

> 已把可验证的真实数字填进正文（102 个单测、12 个 E2E、CI 4 个 job、容器健康检查实测）。剩余 `【待填】` 只有生产上线后才会有的数据（在线链接、访问量、LCP），不要提前编造。

## 1. 三分钟版本（背下来）

「Lumen 是我一个月做的一个 AI 内容中枢，用来同时解决自己的两个问题：自媒体内容分散、以及想做一个能体现全栈能力的作品。它把技术文章、小说连载、学习笔记统一成一套内容模型，前台是公开站，后台是写作台，接了大模型做大纲、润色、摘要，再把全部内容切片向量化，做成可提问的个人知识库。

技术上用 Next.js 15 App Router 做单体全栈，Prisma + PostgreSQL 加 pgvector 同库存关系和向量，AI 走 OpenAI 兼容协议所以换模型只改环境变量。工程上 GitHub Actions 管 lint、类型、单测、E2E 和生产构建，镜像推 GHCR，发布时先做数据库迁移再上线，最后轮询健康检查，失败自动回滚。

最有意思的一块是**每次 AI 调用都落库记账**：token、成本、延迟、失败原因，后台能按天看用量、失败率和 P95，还有月度预算熔断；发布日历把内容节奏也做成可验证的视图。这也是我做这个项目的取舍——不追微服务和花哨架构，而是把单人一个月能完整交付、能被验证的链路做扎实。目前 102 个单测、12 个 E2E 用例、CI 四个 job（质量 / 构建 / E2E / 镜像）全绿，容器健康检查实测通过。【待填：上线后补访问量、AI 调用次数、LCP 的真实数字】」

## 2. STAR 结构（遇到「讲一个最能体现能力的项目」）

- **S**：四条线并行（雅思、减脂、小说、项目），每天只有约 6 小时给项目，一个月必须上线。
- **T**：一个人交付完整前后端 + AI + CI/CD，且内容不能是假数据。
- **A**：单体全栈收敛范围；契约先行（先定 schema、API、服务层接口）；CI 门禁挡住低级错误；AI 调用统一过编排层记账；向量与关系数据同库省运维。
- **R**：四周内 W1–W4 代码全部交付，四个 CI job 全绿，102 个单测 + 12 个 E2E 用例通过，镜像健康检查在真实容器里验证过。【待填：上线链接、CI 时长、发布次数、真实文章数】。

## 3. 八个技术亮点（每个都能往下追两层）

1. **统一内容模型**：三类内容一张表 + `type` 枚举，一套代码搞定列表、搜索、RAG、统计；代价与补法（`metadata Json` 扩展位）能说清。
2. **AI 编排层**：所有调用过 `ai.service`，集中做 prompt、限流、缓存、记账、重试；为什么不放 Route Handler 里。
3. **成本可观测**：`AiJob` 表 + 预算熔断 + 降级策略，能讲「模型不是调通就完事」。
4. **RAG 全链路**：切片策略、重叠窗口、HNSW cosine、带出处回答、防注入、无片段拒答。
5. **Provider 可插拔**：chat 与 embedding 分离，DeepSeek 无 embedding 这个真实坑怎么绕。
6. **CI/CD 门禁与回滚**：构建期占位 env、迁移先于发布、健康检查、`:sha-` 镜像 tag。
7. **安全基线**：JWT + httpOnly + SameSite、Zod 全量校验、日志脱敏、参数化向量检索、限流。
8. **可讲清的取舍**：为什么单体、为什么 pgvector 而不是独立向量库、为什么 `db push` 起步再切 migrate。

## 4. 高频追问与答法

| 追问 | 要点 |
|---|---|
| 为什么不用微服务？ | 单人 4 周，部署与联调成本优先；服务层已隔离，抽出来是渐进的，不需要重写 |
| 向量库为什么选 pgvector？ | 事务一致、零额外组件、规模在 10 万切片内够用；超了再拆 Qdrant，检索接口已隔离 |
| JWT 注销怎么失效？ | 短 TTL + 退出清 Cookie；真正即时失效需黑名单或换 DB Session，说清代价 |
| RAG 怎么保证不胡编？ | 只用检索片段、片段不足拒答、答案带 `contentId/chunkIndex` 引用，并有注入用例测试 |
| AI 超时 / 供应商挂了怎么办？ | 20s 超时 + 1 次重试 + 熔断 + 降级到手动写作，工作台不阻塞 |
| 数据库迁移如何不中断服务？ | 只做加法、分两次发布、迁移先于应用、镜像按 sha 可回滚 |
| 如果 QPS 涨 100 倍？ | 热点文章 ISR + CDN、AI 长任务进队列、读写分离、向量索引调参，逐层说 |
| 项目里最不满意的地方？ | 【待填：诚实的 1 个，比如初期 `db push` 导致迁移历史缺失 / 没做覆盖率门禁，并说明改进计划】 |

- 设计 AI 调用审计表与预算熔断，记录 token/成本/延迟/失败率，后台按天聚合出 P95 与失败率看板。
- GitHub Actions 实现 lint / typecheck / Vitest / Playwright / 镜像构建门禁（102 单测 + 12 E2E），部署前自动迁移、部署后健康检查与按 sha 回滚；【待填：CI 时长 X 分钟】。
